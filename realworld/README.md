# realworld — real compiler output as the readiness proof

Three C programs are compiled **twice**: once natively with the host
compiler (the reference) and once to WebAssembly with
`clang --target=wasm32` (the artifact under test). The engine must
produce the same output as the native build, byte for byte.

| Program | What it exercises | Native == engine |
|---------|-------------------|------------------|
| `qsort_demo.c` | integer ALU, nested control flow, short-circuit `&&`, memory loads/stores | `result: 3286 (i32)` |
| `matmul_f32.c` | 8x8 f32 matrix multiply: f32 mul/add, f32 loads/stores, 3 nested loops | `result: 22.125 (f32)` |
| `crc32_demo.c` | CRC-32 over a fixed message with a 256-entry lookup table in the data section (1 KiB), bit ops, computed memory index | `result: 1157425541 (i32)` |

The expected values are committed in `expected.txt` and checked by
`tests/test_phase14.c` (so `make test` covers the real modules without
a wasm toolchain).

## Building and verifying

```sh
make realworld          # native + wasm build, opcode check, run and compare
make realworld-verify   # run the committed modules through the engine only
```

`make realworld` needs `clang` with the `wasm32` target and `wasm-ld`.
When the distribution packages are not installed system-wide, install
them into a local prefix without root:

```sh
sh tools/setup_wasm_toolchain.sh          # lld + wabt + binaryen
export PATH="$HOME/tools/root/usr/bin:$HOME/tools/root/usr/lib/llvm-18/bin:$PATH"
```

The build uses only MVP features. Every post-MVP construct is switched
off explicitly (`-mno-sign-ext -mno-bulk-memory -mno-mutable-globals
-mno-reference-types -mno-nontrapping-fptoint -mno-multivalue
-mno-extended-const -mno-simd128 -mno-tail-call -mno-exception-handling`)
and the emitted module is checked afterwards: no sign extension, no bulk
memory, no non-trapping conversions, no multi-value, no reference types,
no SIMD, no mutable globals, no imports, at most one result per
function. A module that violates any of these fails the build.

The data the programs use is generated by `tools/gen_realworld_data.py`
(`matmul_data.h`, `crc32_table.h`); the generator self-checks the CRC-32
table against the canonical vector `crc32("123456789") = 0xCBF43926`.

## What this found

Running real compiler output exposed two engine defects (fixed in
`phase5.2`):

1. **Uninitialized locals had the wrong type.** The runtime created every
   local as an i32 zero. Real clang output reads an `f32` local before
   writing it (loop-carried accumulator), which trapped with a type
   mismatch. The linker now keeps the declared local types and the VM
   initializes a local with them (`+0.0f` for f32, `+0.0` for f64).
2. **The fuzz pipeline had no visible memory page**, so every module
   with a data section was rejected with `DATA_OUT_OF_BOUNDS` and the
   data path was never fuzzed. The pipeline now creates one visible page
   like the CLI does.
